Haiku workers throughout. "wteam" = Opus planner, Haiku worker, Sonnet reviewer, 4 pairs,
coupled-ticket planning plus a final integration ticket, codegraph, overlap allow.
Single runs: one per arm, so treat gaps under ~30 tests as noise. Every score was checked
for memorization (verbatim overlap with upstream) and for reads outside the run's repo.

## Conclusion

On greenfield work from a precise written spec, single Haiku matches or beats wteam at
2–10× lower cost, and a plan does not help it. Planning, review and parallel pairs show no
value on these tasks. Untested: underspecified goals, brownfield changes, debugging.

## Code quality (blind review), 2026-10-23

All incidentkit v2 arms pass the tests, so code quality is what differs. Opus judged each module
pair blind (labels X/Y), once in each order, choosing on readability, structure, naming,
duplication, error handling and maintainability.

| Pair | wteam preferred | single preferred | tie |
|---|---|---|---|
| run 1: single Haiku vs wteam | 27 | 3 | 0 |
| run 2 (repeat): single Haiku vs wteam | 22 | 7 | 1 |
| run 1: wteam stand-in reviewer vs wteam Sonnet reviewer | stand-in 24 | reviewed 6 | 0 |

Repeat run scores: single Haiku 2399/2399 ($0.99), wteam 2392/2399 ($5.96).
The judge cited smaller named helpers, one place per rule, located error messages, type hints
and docstrings. The edge comes from the ticket structure (one focused worker per module); Sonnet
reviewers did not add to it in the one run that isolates them.
